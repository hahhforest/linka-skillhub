linka-skillhub 需求到架构设计说明

本文不是页面草图，也不是文档模板。本文用软件工程方法把用户需求转成可实现、可测试、可验收的系统设计：先定义目标和边界，再定义 actor/use case、领域模型、事件流、状态机、架构分层、页面职责和验收测试。后续实现必须逐条映射到本文。

0. 分析方法：如何从需求转成软件工程架构

本项目的正确分析顺序如下。它用于约束团队协作，防止“看到一个按钮就写一个按钮”。

  1. Actor / Goal 建模：识别谁使用系统、每个 actor 想完成什么目标。
  2. Use Case 建模：把目标拆成有起点、终点、主流程、异常流程的用例。
  3. 领域模型：抽取 Agent、Skill、Source、Registry、Review、Distribution 等核心对象，定义关系和不变量。
  4. 事件风暴：按时间顺序列出系统中发生的领域事件，例如 SkillScanned、SkillImported、ReviewCompleted、DistributionApplied。
  5. 状态机：为每个关键流程定义 states、events、guards、side effects、error states。
  6. 架构边界：根据领域对象和状态机划分 core、adapter、API、UI，而不是让 UI 直接拼业务逻辑。
  7. 验收测试：每个 use case 必须有单测、集成测试或浏览器测试，测试先于或同步于 UI 实现。

当前实现的问题不是“文案不好看”，而是跳过了第 1-5 步，直接做 UI，导致功能含义、状态转移、用户确认点都不稳定。

1. 需求模型

1.1 Stakeholders / Actors

Actor目标关注点
用户 / Skill 管理者找到、汇总、审核、分发本机多个 Code Agent 的 skills。不要破坏真实目录；操作含义清楚；能回滚；能同步 GitHub。
Code Agent CLI作为可选审核器，被用户显式选择后执行审核 prompt。不能被静默调用；输出必须可追溯。
本地文件系统承载真实 skills、mirror、registry、backup。路径边界必须严格；symlink 不能逃逸。
GitHub Registry保存汇总后的 skill registry 历史。push 前应有安全检查和用户确认。

1.2 User Goals

ID目标成功标准
G1扫描所有支持的 skill 来源。用户确认扫描后，看到各来源 skill 列表、状态和路径。
G2把 skills 汇总到一个可版本控制的 registry。registry 包含原样 skill 包、manifest、prompt、review。
G3判断 skill 是否合法、可共享、仅限某 Agent 或有风险。审核结果有证据、语言匹配 UI，并可追溯到 prompt 版本。
G4从 A Agent 有选择地复制 skills 到 B Agent。交汇中心展示来源路径、目标路径、copy/overwrite/skip 预览，确认后复制。
G5从 Registry 批量分发 skills 到多个目标 Agent。分发管理展示目标、备份、跳过原因，确认后写入目标。
G6把 registry 推送到 GitHub。GitHub repo 存在，commit 历史可追溯，敏感风险有确认。

1.3 Functional Requirements

IDRequirementPriorityTrace
FR-001系统 MUST 支持 Mavis、Codex、Claude Code、OpenCode、.agents/skills 的 source/target 配置。MustG1,G4,G5
FR-002系统 MUST 默认运行在 mirror profile，真实目录只读复制到 sandbox mirror 后再测试。MustG1,G5
FR-003扫描 MUST 由用户点击并确认后运行，不能页面加载时隐式扫描。MustG1
FR-004审核 MUST 由用户选择审核器后运行；Code Agent 审核不能静默触发。MustG3
FR-005交汇中心 MUST 提供来源路径、目标路径、skill 选择、复制预览、确认复制。MustG4
FR-006分发管理 MUST 用用户可理解的动作名展示 Registry 到多目标的复制流程。MustG5
FR-007系统 MUST 提供中文/英文 UI 和对应语言的审核 prompt。MustG3
FR-008所有写操作 MUST 有路径边界检查，local profile 写入 MUST 二次确认。MustG2,G4,G5,G6

1.4 Non-Functional Requirements

  • Safety：默认不写真实 Agent 目录；API 不信任前端传入的 path。
  • Traceability：scan/import/review/distribution/GitHub sync 都要有结果记录。
  • Explainability：每个按钮必须说明影响范围，不能只显示内部术语。
  • Testability：所有状态转换必须有纯函数测试；核心流程必须有浏览器测试。
  • Extensibility：新增 Agent 只需添加 adapter/profile/source/target，不重写业务流程。

2. 领域架构

2.1 Bounded Contexts

Context职责不负责
Source Discovery根据 profile 找到 source dirs，识别存在性和 scope。不解析 skill 内容，不写 registry。
Skill Catalog解析 SKILL.md、计算 hash、生成状态和证据。不做 LLM 审核，不复制到目标。
Registry保存原样包、manifest、review、prompt snapshot。不决定用户要分发到哪里。
Review规则审核和可选 Code Agent 审核。不扫描 source，不执行分发。
Distribution生成复制预览、备份、复制到目标。不信任 UI 传入 path。
Git Sync提交、推送、拉取 registry。不直接操作 Agent target。
UI Workflow承载用户操作和状态反馈。不包含业务判定和路径安全逻辑。

2.3 Invariants

  • 一个 skill 的主状态桶互斥：problem > agent_bound > shareable > other。
  • Registry path、target path、backup path 必须在 profile 允许根目录内。
  • Distribution apply 前必须由服务端重新生成或校验 plan。
  • Code Agent review 必须保存 reviewer、language、promptVersion。
  • 切换 profile 必须清空当前 scan、selection、plan。

4. 页面如何承载领域工作流

4.1 总览

总览承载 Scan + Source Filter。它不承载 Registry Import、Review、Distribution 的完整流程，只提供进入这些流程的 selection。

  • 左侧 Agent 必须是 filter 控件。
  • 扫描结果列表必须可滚动。
  • 选中 skill 后必须出现可用下一步：审核、交汇、分发。

4.2 审核中心

审核中心是独立页面或弹框流程。它必须展示可用审核器、审核范围、输出语言、写入位置。

4.3 交汇中心

交汇中心只处理 A → B。它必须显示来源和目标的绝对路径，并提供“预览交汇复制”和“确认复制到目标 Agent”。

当前用户指出的问题：选择了 skill 但没有分发按钮。根据状态机，这是 readyToPreview 状态缺少 previewIntersection action 的 UI 承载。

4.4 分发管理

分发管理处理 Registry → 多目标。不要用“生成分发计划/执行分发”作为裸文案；必须改成“预览复制结果/确认复制到选中的目标 Agent”。

4.5 Registry / GitHub

Registry 页面管理导入、Git 状态和远端同步；不做设置，不做交汇，不做分发。

5. 验收测试体系

层级测试目标命令
状态机单测动作合法性、非法转移、guard、错误态。pnpm test -- workflow-state
核心逻辑单测frontmatter、扫描、导入、路径安全。pnpm test
浏览器巡检页面文案、无假按钮、无广告文案、核心页面可达。node scripts/ui-audit.mjs
浏览器流程语言切换、扫描确认、来源筛选、审核弹框、交汇/分发预览。node scripts/ui-flow-test.mjs

团队协作规则：浏览器巡检发现 issue 时，不提交；先把 issue 转成修复任务，修完重跑。只有 issue 为 0 或明确记录为延期项，才允许中文 commit。

6. 实施路线

  1. 修交汇中心：添加来源/目标绝对路径、预览交汇复制、确认复制按钮。
  2. 修分发管理：改文案为“预览复制结果/确认复制”，解释 copy/overwrite/skip。
  3. 实现审核中心：用户选择审核器后运行；检测本机 Agent CLI 可用性。
  4. 实现设置页：语言、profile、路径、安全策略、GitHub。
  5. 补 GitHub 页面：Git 状态、commit、push、pull。
  6. 补完整验收测试：每个 use case 都有状态机测试和浏览器流程测试。

7. 待确认问题

  • 交汇中心是否允许一次从一个来源复制到多个目标，还是严格 A → B？建议 v1 严格 A → B。
  • 默认是否允许导入 invalid/unsafe 到 Registry？建议允许导入但默认禁止分发，并明显标红。
  • Code Agent 审核结果是否必须人工确认后才覆盖规则审核状态？建议必须人工确认。
  • GitHub repo 默认 private 是否固定？建议默认 private，用户显式选择 public。
